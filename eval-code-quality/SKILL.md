# 代码质量评测技能

对指定项目下的一个或多个子项目做 12 维度质量评测,每个子项目总分 10 分,再按固定权重聚合出项目级总分。只评审、不修复。

## 输入

`$ARGUMENTS` 为目标,以下任一形式:

1. **项目目录**(如 `my-project`):自动发现其下全部子项目并全部评测
2. **一个或多个子项目目录**(空格分隔,如 `my-project/backend` 或 `my-project/backend my-project/frontend`)
3. **缺省**:列出仓库根下含 `backend/` 或 `frontend/` 的候选项目,要求用户选择

### 子项目发现规则

给定项目目录后,把其下每个含独立构建清单(`package.json` / `pom.xml` / `build.gradle` / `go.mod` / `Cargo.toml`)且含源码的**一级目录**识别为子项目。发现结果先呈现给用户确认后再开评;识别不到任何子项目时,把项目目录本身当单个子项目评。

## 取证纪律

- **只读评审**:允许 Read / Grep / Glob / `git log` / `ls`;**禁止** npm install / 构建 / 启动服务 / 发网络请求
- 每个分数必须落到具体证据(文件:行号),证据分级沿用 `[C]` 源码读过 / `[V]` 亲手验证 / `[S]` AI 自述(永不作证据)
- 密钥检查:grep `.env` 是否入 `.gitignore`、源码/构建产物中的 key 模式;**输出中严禁出现密钥明文**
- 未实跑得到验证的维度(正确性、性能),JSON 中标 `confidence_limited: true`

## 12 维度与权重(合计 10,不得自创量尺)

| # | 维度 | 权重 | 看什么 |
|---|---|---:|---|
| 1 | 正确性 | 2.0 | 逻辑对不对、边界条件、null/空集合处理、并发问题 |
| 2 | 错误处理 | 1.0 | 异常捕获粒度、失败路径、资源释放、事务回滚 |
| 3 | 安全性 | 1.0 | 注入、越权、密钥硬编码、输入校验、CORS/鉴权 |
| 4 | 可读性与命名 | 1.0 | 命名达意、函数长度、嵌套深度、魔法数字 |
| 5 | 模块化与分层 | 1.0 | 分层是否清晰、职责单一、模块间耦合方向 |
| 6 | 测试 | 1.0 | 有无测试、覆盖关键路径还是摆设、断言质量 |
| 7 | 简洁性 | 0.5 | 重复代码、死代码、过度设计(单实现接口、无用抽象) |
| 8 | 一致性 | 0.5 | 风格/命名/错误返回格式是否全局统一 |
| 9 | 性能 | 0.5 | N+1 查询、循环内 IO、无分页全量查询、明显低效算法 |
| 10 | 类型与契约 | 0.5 | 类型完整度、any/滥用、入参出参校验 |
| 11 | 依赖与配置 | 0.5 | 依赖是否必要、版本可复现、配置与代码分离 |
| 12 | 文档与注释 | 0.5 | README 可跑起来、复杂逻辑有注释、API 文档 |

## 打分方式

每个维度先打**原始分 0–10**(0.5 粒度),按通用锚点:

- **9–10**:全目录无反例,且有正面亮点
- **7–8.5**:个别小瑕疵,无实质问题
- **5–6.5**:有明显问题但不致命,多处反例
- **3–4.5**:该维度系统性缺失或形同虚设
- **0–2.5**:完全缺失,或存在致命缺陷(如硬编码密钥)

**维度得分 = 权重 × 原始分 / 10**,总分 = Σ 维度得分,上限 10。

打分纪律:每个分数必须能回答"什么现象让我给 X 而不是 Y";答不出就回去补证据。宁严勿松,以源码实际为准。

## Findings(问题清单)

- 全部问题编号列出,**数量不设上限**,每个必须含 `file:line`
- 按严重度排序:`blocker`(安全漏洞/数据错误)> `major`(功能性缺陷)> `minor`(质量瑕疵)
- 描述具体到"什么输入/场景下出什么错",不写泛泛的"建议优化"

## 执行流程

1. 解析输入,发现/确认子项目列表
2. 逐个**串行**评测每个子项目(互不影响):
   - 勘察: 目录树、构建清单、代码规模
   - 便宜检查先行: grep 密钥模式、TODO/FIXME、`any` 数量、测试文件数
   - 逐文件精读,按 12 维度取证、记 findings
   - 打分 → 校验
3. 聚合项目级评分 → 写 JSON → markdown 摘要

## 项目级聚合

每个子项目评完后,聚合出**项目维度**总分。项目可能包含任意组合的子项目(前端、后端、多个后端微服务):

- **单个子项目**: 项目总分 = 该子项目总分
- **恰好一个后端 + 一个前端**(识别依据: 目录名/构建清单/源码内容): `项目总分 = 后端 × 0.6 + 前端 × 0.4`(后端承载业务逻辑与数据安全,权重更高)
- **其他任何组合**(≥3 个子项目,或多个后端微服务、多前端等): 按各子项目**源码文件数占比**加权:
  `项目总分 = Σ(子项目总分 × 该子项目源码文件数 / 全部子项目源码文件数)`。文件数从勘察结果取,不用猜
- 多个后端微服务各自独立打分、独立 findings,再按上式聚为一个项目分;**不做**"微服务架构质量"这类架构级额外评分

聚合前先对每个子项目做写前校验,校验不过重算,不得手工改数。项目级 `grade` 沿用同一分档。

## 输出

写入 `<项目目录>/eval-code-quality.json`(不进 git,由用户决定去留),并在回复中以 markdown 给出: **打分逻辑说明 + 汇总评分表 + 各子项目评分表 + findings 摘要**。打分逻辑说明必须讲清三层: ① 12 维度及各自权重;② 单维度原始分 0–10 的锚点与 `维度得分 = 权重 × 原始分 / 10`;③ 子项目分 → 项目分的聚合公式(写出实际代入数字的算式)。
