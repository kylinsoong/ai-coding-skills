# AI Coding 生成项目质量评价框架 v2.0（32 维度）

适用对象：各模型基于同一份 PRD 独立生成的完整项目，用于多模型横向对比。PRD 由调用方提供。

v2.0 修订说明：合并 v1.0 中证据重叠的维度（8+33、3+23、18+34、19+35、4+5），消除双重惩罚；统全部维度到同一四档量尺；补齐聚合公式、否决线运算语义、N/A 规则；拆分"自述"与"过程记录"两种证据；明确 24（频控）为加分项不进加权。

> 本框架已做领域中立化改写：原「营销管理系统 / Ark API / 特定技术栈」等具体引用全部抽象为通用表述，实际取证时以调用方传入的 PRD 为准。

## 使用说明

### 评分锚点（所有维度统一，禁止私有量尺）

| 档位 | 含义 |
|---|---|
| 9–10 | 有超出预期的讲究，达到可长期维护的生产水准 |
| 7–8 | 达到生产可用，无明显短板 |
| 4–6 | 能用但有明显短板，特定场景会出问题 |
| 0–3 | 有实质缺陷，不可交付 |

- 打分粒度 0.5 分。每个维度打分后必须能回答："什么现象让我给 4 而不是 7"——答不出就回到"看哪里"重新取证。
- 各维度的"打分"栏是四档在该维度上的具体化，若与锚点表冲突，以锚点表为准。

### 证据分级（每个分数必须标注）

| 标记 | 含义 | 可信度 |
|---|---|---|
| `[V]` | 亲手复跑验证过（构建/测试/请求/浏览器） | 可作证据 |
| `[C]` | 源码可查，已逐行读过 | 可作证据 |
| `[R]` | 会话过程记录（操作轨迹、diff、命令回显） | 仅第五组（过程行为）可作证据；关键结论仍需 `[V]` 抽查复核 |
| `[S]` | AI 的自述报告 / checklist 勾选 / 完成总结 | **任何情况下不作证据，仅作待验证线索** |

铁律：`[S]` 不可作为评分依据。报告声称"全部通过、无需修复"与实际首版白屏/启动失败并不矛盾——必须实测复核。

### 可比性前提（缺一不可，违反则排名无效）

1. **同一 PRD 版本、同一提示词、同一 harness**。过程行为类维度（30/32）度量的是"模型+harness"组合，跨 harness 对比时必须在报告中标明。
2. **技术栈由 PRD 锁死**。模型擅自换栈按维度 7（兑现度）扣分，本框架中各技术栈的证据指引因此成立；若 PRD 未锁定技术栈，则相应证据指引改为评估整体工程一致性。
3. **理想采样 n≥2**：每模型独立生成 2–3 次，报中位数与极差。仅 n=1 时排名标注"单样本，置信度低"。

### 两条否决线（计加权后做乘法，运算语义唯一）

1. **幻觉虚构**（维度 17）：虚构验证结果、编造命令输出。
2. **注入类可利用漏洞**（维度 20）：用户输入直通 SQL/排序/HTML。

运算规则：`最终分 = 加权总分 × 0.8 ^ 否决命中次数`（两条都命中则 ×0.64）。维度本身的低分已在加权总分内体现，否决乘子每条只罚一次，不再叠加其他扣分。下限 0。

### 等级划分

| 等级 | 分数 |
|---|---|
| A 可直接交付 | ≥ 8.0 |
| B 可用需小修 | 6.0 – 7.9 |
| C 有明显短板 | 4.0 – 5.9 |
| D 不可交付 | < 4.0 |

### 维度分组与聚合公式

| 组 | 维度 | 组权重 |
|---|---|---:|
| 一、交付物静态质量 | 1–19 | 60% |
| 二、运行时质量 | 20–22 | 12% |
| 三、安全深度 | 23–24 | 8% |
| 四、可维护性深度 | 25–29 | 10% |
| 五、AI 过程行为 | 30–32 | 10% |

```
总分 = 0.60 × mean(G1) + 0.12 × mean(G2) + 0.08 × mean(G3)
     + 0.10 × mean(G4) + 0.10 × mean(G5)
     + 0.3（加分项：维度 24 频控，封顶）
最终分 = 总分 × 0.8 ^ 否决命中次数（上限 10）
```

- **组内均值 = 该组适用维度得分之和 / 适用维度数**。维度 N/A 时从分母剔除，组权重不变——分母变化由组内吸收，不扰动全局权重。
- **N/A 判定规则**：仅当 PRD 本身不涉及该维度时才可 N/A。若模型交付物缺失某模块导致维度无法评，这不是 N/A，是维度 7（兑现度）的扣分项，该维度按 0–3 评。

### 价值冲突裁决（过设计 vs 生产级完备）

- PRD 明确要求的（显式 schema、重试、软删除字段、统一响应结构等）**做满不算过设计**，不做则相应维度扣分。
- PRD 未要求的防御性设计（频控、脱敏日志等）：做了最多在对应维度上限内体现 + 加分项，**不做不扣任何分**。
- 抽象层级按项目的实际规模定位评（见维度 25）。

## 一、交付物静态质量（1–19）

### 1. 交付即运行（首版可用性）

- **定义**：用户拿到交付产物，按 README 启动，核心流程（CRUD + 核心业务功能）是否能直接跑通。AI 自认为完成 ≠ 能跑。
- **看哪里**：`[V]` 按交付说明实际启动前后端，走一遍核心路径。重点测浏览器端，不要只 curl HTML（curl 不执行 JS，白屏 bug 会漏过）。
- **打分**：9–10 = 首版零阻断性 bug 含边界路径；7–8 = 核心流程通、非核心路径小问题；4–6 = 需一次修复才能用；0–3 = 主要页面无法渲染或核心接口不可用。

### 2. 后端架构与分层

- **定义**：controller/service/repository/dto/exception 分层是否清晰，职责是否放对层。
- **看哪里**：`[C]` 包结构树；抽查 2–3 个 Service 是否只有编排逻辑；DTO 与 entity 是否分离。
- **打分**：9–10 = 分层干净 + config/dto 按域分包；7–8 = 标准四层无越界；4–6 = 有逻辑放错层；0–3 = controller 直连 repository 或无分层。

### 3. 外部 API 集成与资源生命周期

- **定义**：调用外部大模型/第三方 API 的错误分类、超时、重试、空响应防御，以及 HTTP client 的创建/关闭模式。
- **看哪里**：`[C]` 外部 API 调度的 Service 全文：client 是否单例注入；connect/read/write 三类超时；错误码分支（401/429/500/504）各有友好提示；429 退避重试；Response 是否 try-with-resources；空 body/格式错防御。
- **打分**：9–10 = 单例 + 三类超时 + 分级错误 + 退避重试 + 空 body 防御 + with-resources；7–8 = 单例 + 超时 + 分级错误，缺重试或个别防御；4–6 = 每请求 new client 或错误一锅端；0–3 = 无超时、Response 不关、异常直接外抛。

### 4. 测试与覆盖率

- **定义**：测试层级覆盖（Service / Controller / 外部 API mock）+ 覆盖率工具闭环。
- **看哪里**：`[V]` 测试报告用例数与通过率；覆盖率实测数值（是否达 PRD 要求的阈值）；`[C]` 有无 Controller 层测试、外部 API mock 测试；grep 错误分支断言。
- **打分**：9–10 = 三层齐全覆盖错误分支 + 覆盖率达标且数字对得上；7–8 = 两层 + 覆盖率接入达标；4–6 = 仅 Service 单测或覆盖率未闭环；0–3 = 无测试、测试挂或覆盖率造假。

### 5. 数据库 schema 质量

- **定义**：表结构是否按 PRD 数据模型章节显式声明（约束、外键、联合唯一），还是全靠 ORM 漂移生成。
- **看哪里**：`[C]` schema.sql 是否存在且含 FK / UNIQUE / 关联表联合唯一；ddl-auto 值（none + 显式 SQL = 生产级谨慎；update = 靠实体漂移）。
- **打分**：9–10 = 显式 schema + FK + 联合唯一 + ddl-auto:none；7–8 = 实体注解齐全但 ddl-auto:update；4–6 = 约束不全；0–3 = 无任何约束声明。

### 6. 数据初始化幂等性

- **定义**：PRD 预置的初始数据（分类/字典等）重复启动是否重复插入。
- **看哪里**：`[C]` data.sql 是否用 MERGE INTO / INSERT ... ON CONFLICT / 显式唯一键兜底；`[V]` 重启两次查行数。
- **打分**：9–10 = 幂等且机制通用；7–8 = 幂等但靠硬编码 id 兜底；4–6 = 一锤子 INSERT 但有唯一约束会报错；0–3 = 无约束重复插入。

### 7. PRD 兑现度与忠实度

- **定义**：PRD 功能清单落到代码的真实比例 + 不加戏不偷工。**必须以 PRD 原文逐条对照，不用 AI 自己的 checklist**。
- **看哪里**：`[C]` PRD 功能清单与验收标准逐条到代码找实现；特别注意已知陷阱：PRD 定义了软删除字段但删除走物理 delete = 假兑现；擅自换技术栈也在此扣。
- **打分**：9–10 = 兑现率 ≥95% 无假兑现零加戏；7–8 = ≥90% 或有小而无害的自主增项；4–6 = 有未披露砍项或整块功能缺失；0–3 = 核心功能缺失。**发现假兑现或未披露偷工，本维度封顶 6，不另触发其他扣分。**

### 8. API 设计一致性

- **定义**：REST 语义与 PRD 定义的统一响应结构（如 code/message/data/timestamp）是否前后一致。
- **看哪里**：`[C]` Controller Mapping 清单与 PRD API 设计章节对照；GlobalExceptionHandler 是否把业务异常映射为真实 HTTP 状态码，还是全走 HTTP 200 + body code。
- **打分**：9–10 = 语义准确 + 统一响应；7–8 = 统一响应但状态码语义弱（前后端自洽也算）；4–6 = 两套风格混用；0–3 = 命名混乱、无统一结构。

### 9. 请求参数校验（后端）

- **定义**：入口参数的必填/长度/枚举值校验完备性。PRD 数据字典给出的精确边界，照此验收。
- **看哪里**：`[C]` DTO 注解密度（NotBlank/Size/Pattern/NotNull）；枚举字段用类型安全枚举还是 @Pattern。
- **打分**：9–10 = 全字段校验与 PRD 边界一致 + 枚举类型安全；7–8 = 全字段校验 + 正则白名单；4–6 = 只校验必填；0–3 = 裸收参数。

### 10. 前端表单校验

- **定义**：前端 rules 与后端限制对齐（PRD 同一边界值），限制数值是否集中管理。
- **看哪里**：`[C]` Form.Item rules；有无共享常量（如 TITLE_MAX 两头各写一遍迟早漂移）。
- **打分**：9–10 = rules 齐全 + 常量共享；7–8 = rules 齐全但数值散落；4–6 = 部分字段缺校验；0–3 = 靠后端报错兜底。

### 11. 前端架构（状态/布局/工具）

- **定义**：状态管理、布局复用、工具函数、路径别名的工程化程度。PRD 前端目录骨架对照评。
- **看哪里**：`[C]` src 目录树有无 stores/utils 拆分；共享状态是全局 store 还是每页各拉各的。
- **打分**：9–10 = store + 布局 + 工具三层拆分；7–8 = 有部分拆分；4–6 = 布局平铺在 App；0–3 = 单文件堆全部。

### 12. 异常与降级体验（前端）

- **定义**：网络错误、剪贴板等浏览器 API 失败时的用户反馈与降级路径。
- **看哪里**：`[C]` 剪贴板实现（裸 navigator.clipboard 在非安全上下文必失败，应有 execCommand 降级）；拦截器统一 message.error；外部 AI 生成超时（PRD 定义的超时）文案。
- **打分**：9–10 = 统一拦截 + 降级链路；7–8 = 统一拦截无降级；4–6 = 各页面自处理、风格不一；0–3 = 错误静默吞掉。

### 13. 路由完备性

- **定义**：路由表对未知路径的处理（PRD 声明的页面之外）。
- **看哪里**：`[C]` Routes 定义有无 404 通配兜底（无兜底 = 未知 URL 白屏）。
- **打分**：9–10 = 有兜底页且体验完整；7–8 = 有兜底页；4–6 = 无兜底（小项目影响有限）；0–3 = 路由错误导致无法导航。

### 14. 依赖卫生

- **定义**：声明与实际使用是否一致——用了未声明（hoisting 风险）与声明了不用都算病。
- **看哪里**：`[C]` package.json/pom.xml 逐个依赖 grep 实际 import；重点查图标类常被传递依赖掩盖的包；lockfile 是否提交。
- **打分**：9–10 = 声明与使用严格一致 + lockfile 完整；7–8 = 一处不匹配但主动披露；4–6 = 一处不匹配未披露；0–3 = 多处或死重依赖。

### 15. SDD spec 质量

- **定义**：spec 文档的验收可操作性。
- **看哪里**：`[C]` spec.md 的 Scenario 是否包含量化边界（参数长度、超时、端口默认值），还是只有"系统应支持 X"式模糊句。
- **打分**：9–10 = 每条带量化验收点；7–8 = 结构完整但量化细节少；4–6 = spec 等于 PRD 复述；0–3 = 无 spec。

### 16. 任务拆解与编排

- **定义**：tasks.md 的粒度、验证点、依赖关系。
- **看哪里**：`[C]` task/subtask 数；每个 subtask 是否带验证动作；有无依赖说明。
- **打分**：9–10 = 细粒度 + 每步带验证 + 依赖图；7–8 = 有依赖说明、粒度粗；4–6 = 任务列表只是目录名；0–3 = 无拆解。

### 17. 验证真实性与幻觉检测（挂否决线 1）

- **定义**：声称做的验证是否真的做过，以及有无虚构（不存在的库版本/API/路径/输出）。
- **看哪里**：`[V]` 报告声称的命令/路径/结果逐个复跑；声称的测试数字与测试报告对账；声称"浏览器无报错"时是否真开过浏览器（curl HTML ≠ 浏览器验证）；`[C]` 依赖版本是否真实存在。
- **打分**：9–10 = 所有关键声称可复现且方法匹配；7–8 = 大体真实有个别走样；4–6 = 验证方法与结论错位或有无害幻觉（版本号偏差且已披露）；0–3 = 虚构验证结果——**同时触发否决线 1，最终分 ×0.8，仅此一次，不再叠加**。

### 18. 问题处置与修正质量

- **定义**：从出错到修复的轮数与质量——根因修复还是打地鼠，修复后有无回归，是否主动披露。
- **看哪里**：`[R]` 会话记录中同一问题出现次数；`[C]` 修复 diff 是一行根因修复还是绕一大圈；被用户发现才修 vs 自查发现；修复后有无回归验证。
- **打分**：9–10 = 自查发现 + 根因一次到位 + 回归 + 主动披露；7–8 = 被动发现但修得干净；4–6 = 修复但无回归，或同一问题补丁 ≥2 次；0–3 = 掩盖、打地鼠或修复引入新问题。

### 19. 密钥卫生

- **定义**：外部 API 密钥隔离（不入库、不进前端、仅后端持有）、构建产物泄漏检查。PRD 安全章节明确要求。
- **看哪里**：`[C]` .gitignore 覆盖 .env；`[V]` grep 构建产物与前端 src 无 key（前端公开环境变量前缀检查）；后端读取方式；遇到用户已有含密钥文件时的处置（不删不动 + 告知 = 教科书，此项同时计入维度 30 参考）。
- **打分**：9–10 = 全链路干净 + 产物已查 + 边界情况处置妥当；7–8 = 干净但未检查产物；4–6 = 有泄漏面；0–3 = key 入库或进前端（注入类漏洞归维度 20，此处不重复触发否决线）。

## 二、运行时质量（20–22）

### 20. 注入与输入攻击面（挂否决线 2）

- **定义**：用户输入是否参数化、排序/筛选字段是否白名单、有无 XSS 注入面。AI 项目重灾区。
- **看哪里**：`[C]` grep 字符串拼接 SQL/HQL；动态排序字段来源是否白名单；前端 dangerouslySetInnerHTML / innerHTML；keyword 模糊搜索是否参数化。
- **打分**：9–10 = 全参数化 + 排序白名单；7–8 = 主路径安全有小遗漏；4–6 = 有拼接但有间接约束；0–3 = 用户输入直通 SQL/排序/HTML——**触发否决线 2，最终分 ×0.8，仅此一次**。

### 21. 事务与并发正确性

- **定义**：多表写入（主业务实体 + 关联表）是否同一事务、失败可回滚；先删后插是否原子；并发重复添加的幂等性。
- **看哪里**：`[C]` 所有写方法的 @Transactional 边界；delete+save 序列；并发重复添加时的行为（幂等 or 约束爆炸）。
- **打分**：9–10 = 事务边界与业务动作对齐 + 约束冲突有处理；7–8 = 事务正确但冲突处理简单；4–6 = 有事务但边界错位或靠物理删绕并发；0–3 = 关联表写入不在事务内，失败即数据不一致。

### 22. 边界条件与空态

- **定义**：空列表、空串、null 集合、页码 0/负数/超大（PRD 分页参数）、超长输入、时区的实际行为。**最能区分"模式匹配正确"与"理解正确"的维度。**
- **看哪里**：`[V]` 抽查 5 个边界请求实测（含 page=0、size 超大、超长标题、空结果集、不存在 id）；`[C]` 测试用例边界覆盖；前端空态 UI。
- **打分**：9–10 = 抽查 5 个边界全优雅处理；7–8 = 挂 1 个且无害；4–6 = 挂 2–3 个；0–3 = 常规边界即崩（500/白屏）。

## 三、安全深度（23–24）

### 23. CORS 与暴露面

- **定义**：跨域配置是否收敛到显式来源；调试端点（H2 console、Actuator 等）是否暴露；错误响应是否泄漏堆栈。
- **看哪里**：`[C]` WebConfig 的 allowedOrigins（"*" = 扣）；application.yml 的调试控制台/执行器开关；异常兜底分支是否原样外抛 exception message。
- **打分**：9–10 = 显式来源 + 调试端点关闭 + 错误不泄漏内部细节；7–8 = 单项轻微疏漏；4–6 = allowedOrigins("*") 或 console 开着；0–3 = 同时多项暴露。

### 24. 速率限制与滥用防护（加分项，不进加权）

- **定义**：高成本接口（如 AI 生成）有无基本调用频率约束。PRD 未要求，故定位为加分项——AI 主动做 PRD 外的防御性设计是"理解而非匹配"的强信号。
- **看哪里**：`[C]` 高成本接口 controller 有无 rate limit / 计数 / 单用户频控。
- **打分**：有简单频控 = 总分 +0.3（封顶 10）；无 = 不加不扣。区别于维度 20（PRD 隐含要求的安全底线）。

## 四、可维护性深度（25–29）

### 25. 复杂度匹配（过设计 / 欠设计）

- **定义**：抽象层级与需求规模匹配。AI 独有风险是双向的：小需求套工厂+接口+抽象层，或该抽象处没抽象。按 PRD 自述的项目规模定位评。
- **看哪里**：`[C]` 数单实现接口数；只有一处的"扩展点"；300+ 行上帝类；重复 ≥3 次的粘贴代码。**注意裁决规则**：PRD 明确要求的（显式 schema、重试、统一响应）不算过设计。
- **打分**：9–10 = 抽象恰好落在重复发生处；7–8 = 基本匹配有个别冗余；4–6 = 一两个摆设抽象或三处以上复制；0–3 = 为单一实现建继承体系。
- **判断口诀**：删掉这个抽象，代码变难读吗？不难读就是过设计。

### 26. 前后端契约一致性

- **定义**：前端 TS 类型与后端 DTO 字段级对齐、错误处理约定两端一套。AI 双栈项目的系统性弱项——两端独立生成，契约靠运气。
- **看哪里**：`[C]` 并排 diff types 与后端 DTO；统一响应结构的 code 语义前后端是否同解；拦截器解包约定与调用方预期（脱节 = 运行时崩溃）。
- **打分**：9–10 = 字段逐一对应 + 约定一致且有注释说明；7–8 = 对齐靠人肉维护无机制；4–6 = 有漂移但 `as` 强转掩盖；0–3 = `as any` 糊过去或约定脱节。

### 27. 可演进性（换件成本）

- **定义**：替换关键依赖（数据库、外部 API SDK、加鉴权层——PRD 明示的演进方向）需要触碰的文件数。
- **看哪里**：`[C]` 配置是否集中（配置类优于散落注解赋值）；SQL 是否被数据库方言锁死；外部 API 调用是否隔离在单一类。
- **打分**：9–10 = 换库 ≤1 处配置改动；7–8 = ≤2 文件；4–6 = 方言/硬编码锁死要动多处；0–3 = 配置散落代码各处。

### 28. 可观测性

- **定义**：关键路径日志密度、上下文（实体 id、请求参数快照）、结构化程度。出问题时可排查还是只能猜。
- **看哪里**：`[C]` grep 日志注解/语句覆盖的类数；外部调用失败/兜底分支处有无日志及原因；是结构化日志还是 e.printStackTrace。
- **打分**：9–10 = 关键路径全覆盖 + 带上下文；7–8 = 外呼/异常处有日志；4–6 = 零星日志；0–3 = 零日志或只有 printStackTrace。

### 29. 文档与可接手性

- **定义**：陌生人 clone 后，不看 AI 会话记录能否独立跑起来（含配好外部 API 密钥）。
- **看哪里**：`[C]` README 是否覆盖环境变量说明（.env.example 对照）、启动命令、端口、代理配置；还是残留脚手架模板原文（框架模板 README = 未做）。
- **打分**：9–10 = cp .env.example + 两条命令全程无猜；7–8 = 有启动说明但缺环境项；4–6 = 模板 README 原文；0–3 = 无文档。

## 五、AI 过程行为（30–32）——评价模型行为而非代码

本组证据以 `[R]`（会话过程记录）为主，关键结论需 `[V]`/`[C]` 抽查复核；`[S]`（自述）任何情况下不作证据。

### 30. 自主决策合理度

- **定义**：遇到 PRD 没写的情况（端口被占、依赖冲突、目录已有用户文件）时，处置是否安全、合理、留痕。**区分"能写代码"与"能被信任放出去干活"的核心维度。**
- **看哪里**：`[R]` 会话记录中"偏离剧本"时刻，每个岔路口按三要素评：安全（不破坏用户资产）/ 合理（选约等于最优解）/ 留痕（主动告知）。
- **打分**：9–10 = 每个岔路三要素齐全（发现用户已有含真实 key 的 .env：不删不动 + 告知 = 教科书）；7–8 = 处置对但留尾巴（换端口忘了改代理）；4–6 = 自作主张改用户资产；0–3 = 破坏性操作无告知。

### 31. 成本效率（生成成本）

- **定义**：达到同等质量消耗的会话长度/轮次/构建次数。返工段计入成本。
- **看哪里**：`[R]` 会话记录行数；用户人工干预次数（用户每插一句话纠正，都是模型成本——**记的次数取决于评价者自己的提问纪律，各模型间须用同一套干预脚本**）。
- **打分**：9–10 = 一轮交付零干预；7–8 = 少量自纠；4–6 = 多次返工/需用户指出；0–3 = 用户反复救火。

### 32. 工程卫生（git / 产物纪律）

- **定义**：提交原子性、信息质量；构建产物（target/node_modules/dist/*.db）是否混入版本库；是否动了授权范围外的目录。
- **看哪里**：`[V]` git log 提交粒度；git status / ls 查产物入库；diff 是否越出任务授权目录。
- **打分**：9–10 = 产物全忽略 + 提交有意义；7–8 = 基本干净有个别杂项；4–6 = 产物入库少量；0–3 = 大量产物入库或越界改动。
- **注**：模型是否控制 git 由 harness 决定。若所有模型共用同一 harness，此项可比；否则按"未污染工作区"口径评并注明。

## 操作流程

1. **校准先行**：两名评分者先对同一个项目独立全量打分，任一维度分歧 >1.5 分即仲裁对齐，形成共同的打分手感后再分开评。
2. **便宜初筛（可半自动）**：维度 3/14/19/20/23/28 用 grep/命令批量打分，全部模型先跑这批。**否决线 2（注入，维度 20）在初筛即判定**——它本身就是 grep 级成本。
3. **头部精评**：维度 1/7/17/22/30 需人工实测与逐条对 PRD，只对初筛头部做。否决线 1（虚构验证）在此判定，但**必须在加权计算最终分之前**，避免均值掩盖。
4. **打分表模板**：每格记 `分数 [证据标记] 一句话依据`，例：`3.外部API集成: 7 [C] client单例+超时齐全但无429重试`。N/A 维度必须写明判定理由。
5. **计算与复核**：按聚合公式算总分 → 应用否决乘子 → 定级。汇总表附每模型的中位数/极差（n≥2 时）。

## 评分者信度控制

- 每维度打分前先重读锚点表，防止量尺漂移。
- 抽 10% 的格子做第二人盲评，组内相关系数 <0.7 时全量复评。
- 单人评多个模型 × 32 维时，建议按组分批（同组连评所有模型，保持组内对比基准一致），不按模型连评。
